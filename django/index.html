Workflow-First Backend Guide

Django

A practical Django handbook organized in the same order used in class: set up the environment, install the packages early, create the project, wire PostgreSQL in Docker, build apps and models, run migrations, then use fixtures and the admin site to keep moving.

Daily Django Workflow

Work through the milestones in order. Each card unlocks the next one, and progress is saved in localStorage on this browser.

1 Setup

Environment Setup

Deactivate any old virtual environment, create a fresh .venv, activate it, and ignore it in Git.

2 Shell

Terminal Quality of Life

Add your alias before creating the project. alias pm="python manage.py" means pm now runs python manage.py. After this step, the workflow uses pm.

Install Dependencies Early

Install the Python packages you know you will need up front so the workflow stays smooth later.

4 Project

Create the Project

Start the nested Django project first, then wait to freeze dependencies until the environment is actually complete.

5 PostgreSQL

Build PostgreSQL in Docker

Create the database image, put both containers on the same Docker network, and confirm PostgreSQL is reachable.

6 Settings

Configure Settings

Point Django at PostgreSQL, update ALLOWED_HOSTS, and make sure the Django container is running on the same network.

7 Freeze

Freeze Dependencies at the Right Time

Freeze after the environment has the packages you actually need, not after every single install step.

8 App

Create student_app

Start the app inside the Django container. This creates the app folder, migrations folder, and starter files you will use for the rest of the assignment.

9 Settings

Add the App to INSTALLED_APPS

Django has to know the app exists. If you forget this step, you get no models, no migrations, no admin entry, and no database tables for the app. 

INSTALLED_APPS = [
    ...
    "student_app",
]
10 Model

Create the Student Model

Define the schema in student_app/models.py before you worry about the admin site or fixtures. 

from django.db import models


class Student(models.Model):
    first_name = models.CharField(max_length=30)
    last_name = models.CharField(max_length=30)
    grade = models.IntegerField(default=9)
    notes = models.TextField(default="No notes yet.")
    is_active = models.BooleanField(default=True)

    def __str__(self):
        return f"< Student: {self.first_name} {self.last_name} >"

    def next_grade(self):
        self.grade += 1
        self.save()
11 Admin

Register the Model in admin.py

This step is required for Student to appear in the Django Admin interface. If you skip it, the admin site loads, but your model is missing from the sidebar. 

from django.contrib import admin
from student_app.models import Student

admin.site.register(Student)
12 Migrations

Run Migrations

Run these inside the Django container after model changes. The first command creates migration files. The second updates PostgreSQL. Then verify the table exists.

13 Admin

Use Admin, Shell, and Fixtures

Create a superuser, test model behavior in the shell, and dump JSON fixture data after you add or update records.

14 Support

Troubleshoot Before You Spiral

Most class problems were one of these: wrong app registration, forgot migrations, wrong container, wrong host, or permissions.

Reference

Workflow Philosophy

This page follows the class workflow, not generic Django docs. Install what you know you need early, then freeze once the Python environment is complete enough to reuse.

Why Django

Batteries Included

Framework

Django is opinionated and batteries included. You get models, admin, migrations, auth, routing, forms, and a lot of backend structure without hunting for third-party packages first.

Models → Migrations → Admin → API Work

Project Rule

Each Project Gets Its Own Virtual Environment

Venv

Treat the virtual environment like node_modules: it belongs to the project, it stays out of Git, and it protects each app's Python version and package list from the rest of your machine.

VS Code usually detects the venv. If not, use Ctrl + Shift + P and choose Python: Select Interpreter.

Install Strategy

Front-Load Known Packages, Delay pip freeze

Smooth Workflow 
python -m venv .venv
source .venv/bin/activate
alias pm="python manage.py"
pip install django "psycopg[binary]" django-stubs
django-admin startproject school_proj
cd school_proj
pm runserver
pip freeze > requirements.txt

Your notes make the better workflow explicit: collect the packages you know you will need, install them early, and freeze after the environment is ready to share or build in Docker.

Project vs App

A Django project is the whole application. Inside it, each app should own one area of responsibility.

App Examples

If your project has students, teachers, and courses, those are good candidates for separate Django apps.

Register Everything

If Django does not know about the app or package in INSTALLED_APPS, you will not get models, migrations, admin entries, or tables.

Configuration

Settings and PostgreSQL

The database and Django server need to be on the same Docker network, and Django needs PostgreSQL settings that match your container names and credentials.

DB Dockerfile

FROM postgres:15

ENV POSTGRES_USER=student
ENV POSTGRES_PASSWORD=student
ENV POSTGRES_DB=school_db

EXPOSE 5432

CMD ["postgres"]

run_db.sh

#!/bin/bash

docker build -t db-img .
docker run -d --rm --name db-container --network school-network db-img

Django Dockerfile

FROM python:latest

WORKDIR /app
COPY . .
RUN pip install -r requirements.txt

EXPOSE 8000

CMD ["python", "manage.py", "runserver", "0.0.0.0:8000"]

run_server.sh

#!/bin/bash

docker build -t django-img .
docker run --rm -it \
  --name django-container \
  --network school-network \
  --user "$(id -u):$(id -g)" \
  -p 8001:8000 \
  -v "$(pwd):/app" \
  django-img

Key settings.py Values

ALLOWED_HOSTS = ["localhost", "127.0.0.1"]

DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": "school_db",
        "USER": "student",
        "PASSWORD": "student",
        "HOST": "db-container",
        "PORT": "5432",
    }
}
Your notes also mention using ["*"] for ALLOWED_HOSTS during development. That is fine for quick class setup, but be deliberate about it.

ORM

Models and Migrations

Models describe the schema. makemigrations creates the change files. migrate applies them to PostgreSQL.

Create the App

pm startapp student_app

Run this in the Django container. Then add "student_app" to INSTALLED_APPS.

Example Model

from django.db import models


class Student(models.Model):
    first_name = models.CharField(max_length=30)
    last_name = models.CharField(max_length=30)
    grade = models.IntegerField(default=9)
    notes = models.TextField(default="No notes yet.")
    is_active = models.BooleanField(default=True)

    def __str__(self):
        return f"< Student: {self.first_name} {self.last_name} >"

    def next_grade(self):
        self.grade += 1
        self.save()
Django Field SQL Equivalent Typical Use
CharField VARCHAR Names, short labels, types
TextField TEXT Longer notes and descriptions
IntegerField INTEGER Grades, counts, numeric state
BooleanField BOOLEAN Flags like is_active
DateTimeField TIMESTAMP Timestamps

Always In Order

Migration Flow

Database
Edit models.py → pm makemigrations → Review migration file → pm migrate → Verify with \dt or \d
If you changed the model but skipped migrate, the database did not change yet.

Data

CRUD and Django Shell

The shell is the fastest place to test your model logic before you wire it into views or APIs.

Object Lifecycle

Create Python object → Modify attributes → save() → Database row

Admin First, SQL Second

Create data through the shell or admin, then verify in PostgreSQL if you need proof that the ORM actually wrote the row.

Create and Save

pm shell

from student_app.models import Student

s = Student(
    first_name="Ada",
    last_name="Lovelace",
    grade=11,
)

s.save()

Read and Update

from student_app.models import Student

s = Student.objects.get(id=1)
s.next_grade()
s.notes = "Met after class for extra help."
s.save()

Basic CRUD Reference

Create Instantiate the model and call save().
Read Use objects.get() or objects.all().
Update Change attributes, then call save().
Delete Call instance.delete() when you need to remove a row.

Schema

Relationships

The lecture material mostly focused on verifying relationships from PostgreSQL with \d, but this is the Django side you will need when your project grows past a single table.

ForeignKey

Use this when many students belong to one cohort or advisor. 

cohort = models.ForeignKey(
    "cohort_app.Cohort",
    on_delete=models.CASCADE,
)

OneToOneField

Use this for one record that extends a single student, like a profile or a locker assignment. 

profile = models.OneToOneField(
    Student,
    on_delete=models.CASCADE,
)

ManyToManyField

Use this when students can enroll in many courses and courses can have many students. 

courses = models.ManyToManyField("course_app.Course")

Verify in PostgreSQL

docker exec -it db-container bash
psql -d school_db -U student
\d
\dt

Use this to confirm tables and relationships were actually created the way you expected.

Data Sharing

Fixtures and Backups

Fixtures are useful for demo, seed, and test data. They are not a full PostgreSQL backup.

Dump Fixture Data

mkdir -p student_app/fixtures
pm dumpdata student_app.Student --indent 2 > student_app/fixtures/student_data.json

If you were testing in the Python shell first, exit the shell before running dumpdata.

Restore Fixture Data

pm migrate
pm loaddata ./student_app/fixtures/student_data.json

Run migrate first so the tables exist before you try to load the JSON.

When You Need a Real Backup

pg_dump school_db > backup.sql

A SQL dump captures the actual database structure and rules in a way fixtures do not.

Daily Startup

This is the shortest path back into a project the next day.

cd db
./run_db.sh

psql -U student -d school_db

Your notes call out a class habit worth keeping: bring both containers up first, verify the DB connection, then enter the Django container and migrate before assuming your data is missing.

Quick Reference

Useful Commands

docker ps See which containers are actually running.
docker exec -it django-container bash Enter the Django container.
docker exec -it db-container bash Enter the PostgreSQL container.
docker network inspect school-network Verify both containers joined the same network.
pm migrate Apply migration files to PostgreSQL.
pm createsuperuser Create the admin login.
http://localhost:8000/admin Open Django Admin.

When Something Breaks

Troubleshooting

These are the class mistakes and environment problems that came up repeatedly.

Forgot INSTALLED_APPS

Symptom: no models, no migrations, no admin entry, and no database table. Fix the app registration first.

Forgot makemigrations or migrate

Symptom: your model file changed but PostgreSQL still looks the same. Run both commands inside the Django container.

relation does not exist

Usually the migration was never applied, or you connected to the wrong database after recreating containers.

Docker Networking

If Django cannot reach PostgreSQL, inspect the Docker network and confirm the DB host in settings.py matches the container name.

Permissions and EACCES

If files were created as root, Linux users may need a user-mapped Docker run or to fix ownership with sudo chown -R $USER:$USER ....

Wrong Database

Verify the DB name you chose in the Dockerfile matches the DB name in psql and settings.py.

PostgreSQL Connection Errors

Check docker ps, confirm port 5432, verify credentials, and confirm the DB container started successfully.

Fixture Confusion

Fixtures are JSON model data, not a full database backup. Run migrations before loaddata.

Admin Looks Wrong

Add __str__ to the model so the admin stops showing object numbers without useful names.
